# メモ帳アプリテスト共通事項

## 1. 目的

React、Express、SQLiteで構成されたメモ帳アプリについて、画面・API・DB・ファイル・認証の結合動作、データ整合性および要件への適合を確認する。

- メモ、ユーザー、タグ、下書き、添付ファイル、画像を正常に操作できること
- 管理者・一般ユーザー・未ログインの権限制御が正しいこと
- 入力エラー、通信エラー、競合時にデータが失われず、重複登録されないこと
- 登録、更新、削除後に一覧・詳細・DB・ファイルが整合すること

## 2. 確認範囲

- ログイン、ログアウト、セッション、権限制御
- メモの一覧、検索、詳細、作成、編集、削除
- タグ、お気に入り、ページング、並び替え
- 下書きの自動保存・復元・削除
- ユーザー一覧、作成、編集、無効化
- 添付ファイル・画像の追加、削除、プレビュー、ダウンロード
- 入力チェック、エラー処理、同時編集制御、二重送信防止
- API、SQLite DB、アップロードファイルの整合性

仕様に存在しない機能は対象外とする。対象外の観点は理由を記録する。

## 3. 比較基準

- 確認対象は`C:\ai-Coding-traning\MemoPad_hands-on`で稼働するメモ帳アプリとする。
- 期待結果は[要件定義](../../docs/requirements.md)と承認済みの仕様変更を基準とする。
- 対象コミット、Node.js・npm・ブラウザのバージョン、実行日時を記録する。
- 同じ初期データ、入力値、権限、操作条件で再実行できるようにする。
- 日時、採番ID、セッションIDなどの変動値は、形式・更新有無・関連付けで確認する。
- 実装と仕様に差異がある場合は実装を正とせず、不具合または確認事項として記録する。

## 4. 環境管理

- OSはWindows 10またはWindows 11、タイムゾーンは`Asia/Tokyo`とする。
- Node.jsはLTS版、フロントエンドはReact + Vite、バックエンドはExpress、DBはSQLite + better-sqlite3を使用する。
- React画面は`http://localhost:5173`、Express APIは`http://localhost:3001`を使用する。
- DBは`data/memo.db`、添付ファイルは`uploads/attachments/`、画像は`uploads/images/`に保存する。
- テスト開始前にDB・アップロード先の書き込み権限および使用ポートを確認する。
- 本番データを使用せず、テスト用DB・ユーザー・ファイルを使用する。
- 管理者、一般ユーザー、無効化ユーザーを準備する。
- 秘密情報、認証トークン、パスワード、個人情報をGit・実行結果・実行ログに保存しない。
- 起動はプロジェクトルートで`npm install`、`npm run dev`を実行する。

## 5. テスト共通観点

### 5.1 ケースの記載・管理

- 機能ごとにテスト観点またはテスト仕様を作成する。
- 各ケースには一意のIDを付与し、観点・テストコード・実行結果・不具合を同じIDで対応付ける。
- 観点IDは[テスト観点表](../test-spec/viewpoint-table.md)の命名規則に従う。
- 各ケースには、ケースID、対象機能、目的、種別、重要度、前提条件、使用データ・権限、操作、入力値、期待結果、確認対象、確認方法、参照元を記載する。
- 確認方法はPlaywright、API、SQLite照合、ファイル照合、手動確認のいずれかを明記する。
- 未実装、自動化対象外、スキップのケースは理由と代替確認方法を記録する。

### 5.2 正常系・準正常系・異常系

- 正常系: 有効な入力と通常操作により、登録・更新・削除・表示が期待どおり完了するケース。
- 準正常系: 入力エラー、検索結果0件、キャンセル、下書き復元などに対して、仕様どおりに案内・中断・再操作できるケース。
- 異常系: 通信失敗、サーバーエラー、競合、権限外アクセスに対して、エラー処理とデータ整合性が保たれるケース。
- 異常系では、部分保存、二重登録、意図しないファイル保存、不要な更新がないことも確認する。

### 5.3 バリデーション・境界値

- 必須、形式、文字数、許容文字、重複、件数、サイズ、拡張子を確認する。
- 未入力、空文字、空白のみ、改行のみ、0、NULL相当を区別して確認する。
- タイトルは0、1、100、101文字、本文は0、1、2,000、2,001文字を確認する。
- タグは0、1、10、11個、名称1、30、31文字、重複を確認する。
- 添付ファイルは0、1、5、6件と10MB境界、画像は0、1、10、11件と5MB境界を確認する。
- ページングは0件、1件、表示件数ちょうど、表示件数+1件、最終ページの端数を確認する。
- エラーの対象項目、文言、表示位置、入力値保持、修正後の再実行を確認する。
- 画面側の制限だけでなく、必要に応じてAPIのサーバー側検証も確認する。

### 5.4 キャンセル・入力保持

- 新規作成・編集画面で変更後にキャンセルした場合、破棄確認を表示する。
- 「編集を続ける」では入力内容を保持し、「破棄する」では登録・更新せず指定画面へ戻ることを確認する。
- 削除確認でキャンセルした場合、メモ・関連ファイル・画像が変更されないことを確認する。
- 自動保存済みの下書きと、手動保存前の変更を区別して期待結果を定める。

### 5.5 認証・権限・セキュリティ

- 未ログイン時は保護画面・保護APIを利用できないことを確認する。
- 一般ユーザーは自分のメモだけを操作でき、他ユーザーのメモIDやファイルIDを直接指定しても操作できないことを確認する。
- 管理者は全ユーザーのメモとユーザー管理を操作できることを確認する。
- 無効化ユーザーのログイン、および無効化後の既存セッションの挙動を確認する。
- HTML・JavaScript相当文字列を実行せず文字列として表示し、XSSが発生しないことを確認する。
- パスワードは平文保存・表示・レスポンス出力されないことを確認する。

## 6. テスト仕様書

### 6.1 格納先

- 要件定義: `docs/requirements.md`
- 実装方針: `docs/implementation-plan.md`
- 共通ルール: `tests/rules/common-test-information.md`
- テスト観点表: `tests/test-spec/viewpoint-table.md`
- Playwright向けケース: `tests/test-cases/playwright-test-cases.md`
- Playwrightコード: `tests/e2e/` 配下
- 実行結果・エビデンス: `tests/results/` 配下
- 実行ログ: `tests/logs/` 配下

### 6.2 構成・命名

- ファイル名とディレクトリ名は、機能と内容を識別できる名称とする。
- Playwrightテスト名にはケースIDと期待する振る舞いを記載する。
- 実行ログ名はテスト種別と実行日時を含める。例: `e2e-20260915-153045.log`
- スクリーンショット、動画、トレース、エラー詳細は、実行結果からケースIDで特定できる名称にする。

### 6.3 一覧・参照方法

- 文書間のリンクはリンク元ファイルを基準とした相対パスで記載する。
- 要件、観点、テストコード、詳細書の変更時は、関連するケースIDとリンクを更新する。
- 実装済み・未実装・自動化対象外の状態と、実行結果の判定は区別する。

## 7. テストケース作成共通ルール

### 7.1 目的・対象工程

機能別のテスト観点、Playwrightテストコード、テスト実行結果を作成・確認する際は、「案の提示、再レビュー、保存、保存後確認」の順で実施する。

### 7.2 作成フロー・成果物

| 工程 | 直接のインプット | アウトプット |
|---|---|---|
| 1. 観点確認 | `docs/requirements.md`、`tests/test-spec/viewpoint-table.md` | 機能別の観点・不足観点 |
| 2. テストコード | 観点表、対象画面・API実装 | `tests/e2e/<機能名>.spec.ts` |
| 3. 実行・記録 | Playwrightコード、環境、テストデータ | `tests/results/`、`tests/logs/` |

- 前工程の成果物を次工程の直接のインプットとして使用する。
- 仕様に疑義がある場合は推測で確定せず、確認事項として記録する。
- テストコードに実装できないケースは、代替確認方法を観点表に残す。

### 7.3 テスト観点の作成

- テスト観点表を基準に、対象機能の正常系・準正常系・異常系・境界値・権限・セキュリティを確認する。
- 各ケースは画面表示だけでなく、必要に応じてAPIレスポンス、DB、関連ファイルまで確認する。
- 対象外の観点は理由を記録する。

### 7.4 Playwrightテストコードの作成

- テスト名にケースIDと期待する振る舞いを記載する。
- 準備、操作、アサーション、後片付けを実装する。
- テストデータはケースごとに分離し、実行順・残存データに依存させない。
- 固定時間の待機を避け、画面状態またはAPI完了を待機する。
- UIから確認できないDB・ファイル整合性は、APIまたは補助処理で確認する。
- モックを使うケースは明示し、実環境との結合確認済みとは扱わない。

### 7.5 再レビュー・保存後の確認

- 観点、テストコード、実行結果をケースIDで照合し、漏れ・重複・不一致を確認する。
- 保存後は、レビュー済みの内容とファイル内容、リンク、ケースIDが一致することを確認する。
- 文書の整合性確認とテスト実行結果を分けて報告し、未実行のケースをOKと扱わない。

## 8. 結合動作の確認

- 入力、保存、再表示、検索、詳細、更新、削除までの一連の処理を確認する。
- メモ更新後に一覧、詳細、タグ、お気に入り、下書き、添付ファイル、画像の状態が整合することを確認する。
- ユーザー無効化後、ログイン・権限・既存セッションが仕様どおりであることを確認する。
- 検索、タグ、お気に入り、ページング、並び替えを組み合わせても期待どおりのデータが表示されることを確認する。
- 保存失敗、通信失敗、競合、キャンセル時に部分保存や不要な副作用がないことを確認する。
- ファイル・画像は追加できることだけでなく、削除、表示、ダウンロード、アクセス制御も確認する。

## 9. データ整合性の確認

### 9.1 テスト前の準備

- テスト用DBを使用し、必要に応じてバックアップまたは初期化方法を確認する。
- テストデータにはケースIDまたは識別可能な接頭辞を付ける。
- 管理者、一般ユーザー、無効ユーザー、および各ユーザーのメモを準備する。
- アップロード用ファイルは許可・不許可形式、サイズ境界を確認できるものを用意する。

### 9.2 登録・更新・削除の確認

- メモIDは編集で変更されず、作成日時は保持され、更新日時だけが更新されることを確認する。
- 削除済みメモが一覧・検索・直接アクセスで利用できないことを確認する。
- ユーザーID・メールアドレスの一意性、タグのメモ内重複防止、お気に入りのユーザー単位保持を確認する。
- 添付ファイル・画像が正しいメモに紐付き、削除済みデータを取得できないことを確認する。
- DBの値、画面表示、APIレスポンスで差異がないことを確認する。

### 9.3 下書き・競合の確認

- 下書きがユーザーと新規作成またはメモID単位で分離されることを確認する。
- 本登録・本更新後に不要な下書きが削除されることを確認する。
- 保存時に`updatedAt`の差分を検出し、競合では更新せず入力内容を保持することを確認する。

## 10. Playwright自動テスト

- Playwright設定は`playwright.config.ts`を使用し、ChromiumでE2Eを実行する。
- 画面横断の確認、ログイン状態、テストデータの準備・後片付けを各ケースで明示する。
- 失敗時はスクリーンショット、トレース、エラー詳細を確認し、ケースIDに紐付ける。
- 並列実行で競合するデータは分離する。競合制御テストは意図した複数セッションで実行する。
- API・DB・ファイル照合が必要なケースは、画面操作だけでOKと判定しない。

## 11. 実行結果・不具合管理

- 実行結果は`tests/results/`、実行ログは`tests/logs/`に保存する。
- 実行結果には、ケースID、対象環境、実行日時、実行コマンド、判定、所要時間、期待結果、実際の結果、エラー内容、関連エビデンス、関連不具合を記録する。
- 判定は`OK`、`NG`、`未実施`、`QA`、`保留`、`N/A`を使用し、実施して期待結果を満たした場合だけ`OK`とする。
- `NG`では期待結果と実際の結果、不一致の事実、再現条件を記録する。推測は確認済み事実と区別する。
- 標準出力、標準エラー出力、開始・終了時刻、失敗原因をログに記録する。
- 認証トークン、パスワード、個人情報、DB接続情報を結果・ログ・エビデンスへ出力しない。
- リトライで成功した場合は、不安定な原因を確認し、初回失敗をOKへ置き換えない。
- 不具合は、製品、環境、テストデータ、テストコードのいずれかへ切り分ける。
- `NG` 判定となったテストは、不具合チケットを作成し、`tests/results/bug-tickets/` 配下にケースID単位で保存する。
- 不具合チケットの格納先は `C:\ai-Coding-traning\MemoPad_hands-on\tests\results\bug-tickets` とする。
- 不具合チケットのファイル名は `BUG-<ケースID>.md` 形式とし、例として `BUG-TC-MEMO-LIST-006-01.md` のように命名する。
- 不具合チケットには、概要、対象テスト、期待結果、実際結果、再現手順、エラー内容、証跡、優先度、備考を記載する。
- 証跡には、実行結果レポート、JSON結果、ログ、HTMLレポート、trace / artifact など、原因調査に必要なファイルパスを記載する。
- テストコード起因の可能性がある失敗も、原因を断定せず不具合チケットとして登録し、備考に「テスト locator 要確認」などの調査観点を残す。

## 12. 完了条件

以下をすべて満たした場合に、対象範囲のテストを完了とする。

- [ ] 必須ケースが実施され、期待結果を満たしている。
- [ ] ログインからメモ作成、検索、編集、削除までの主要フローが完了する。
- [ ] 管理者・一般ユーザー・未ログインの権限制御が確認できている。
- [ ] 登録・更新・削除、下書き、タグ、お気に入り、添付ファイル、画像の整合性が確認できている。
- [ ] データ消失、不正更新、二重登録、権限逸脱につながる不具合が解消している。
- [ ] 未実施、QA、保留、N/A、自動化対象外のケースと理由が明確である。
- [ ] 対象コミット、環境、テストデータ、実行結果、ログ、エビデンスを追跡できる。

未解決の不具合や未実施ケースがある場合は、理由と対応方針を記録しただけでテスト完了とはしない。
