# メモ帳アプリQA共通ルール（レビュー反映版）

## 1. 適用範囲

本書は、React、Express、SQLiteで構成されたメモ帳アプリの画面、API、DB、認証、権限、ファイル処理をテストする際の共通ルールとする。既存の要件定義および実装仕様を優先し、仕様が未定義の項目はテスト実施前に合意する。

## 2. テスト分類と優先度

テストケースには、次の項目を付与する。

- 種別: 正常系、異常系、境界値、権限、セキュリティ
- 対象: 画面、API、DB
- 重要度: 高、中、低

重要度「高」は、ログイン、メモ登録・更新・削除、権限確認、データ消失、ファイルアクセス制御とする。

## 3. HTTPステータスの期待値

| ステータス | 期待する用途 |
|---|---|
| `200` | 取得、更新、削除の成功 |
| `201` | 登録の成功 |
| `400` | 入力値またはリクエスト形式のエラー |
| `401` | 未認証またはログイン失敗 |
| `403` | 権限不足 |
| `404` | 対象データなし |
| `409` | 重複または同時編集競合 |
| `500` | サーバー内部エラー |

レスポンス本文、HTTPステータス、DB状態を一体で判定する。

## 4. 認証・権限ルール

- 管理者は全ユーザーのメモを閲覧、編集、削除できる。
- 一般ユーザーは自分が作成したメモだけを操作できる。
- 一般ユーザーはユーザー管理画面とユーザー管理APIを利用できない。
- 一般ユーザーが他ユーザーのメモIDを直接指定しても参照、変更、削除できない。
- 無効化ユーザーはログインできない。
- 無効化後の既存セッションは、実装仕様に従って確認する。仕様が未定義の場合は保護APIも拒否する方式を推奨する。
- 認証トークンやパスワードをログ、テスト結果、画面キャプチャに記録しない。

## 5. テストデータ管理

- 本番DBを使用しない。
- テスト用ユーザー、メモ、タグ、ファイル、画像、下書きには識別可能な接頭辞を付ける。
- テストケース間で前のケースのデータに依存しない。
- テスト開始時に管理者、一般ユーザー、無効ユーザーを確認する。
- テスト終了後はテストデータを削除または論理削除する。
- DB初期化前に、対象がテスト用DBであることを確認する。
- 再現に必要な初期管理者アカウントは削除しない。

## 6. 日時ルール

- 画面表示形式は `YYYY/MM/DD HH:mm:ss` とする。
- 保存日時と表示日時のタイムゾーンを記録する。
- 編集時にメモIDと作成日時が変わらないことを確認する。
- 編集時に更新日時だけが更新されることを確認する。
- 更新後の更新日時が更新前より新しいことを確認する。
- 同一秒に複数回更新した場合の扱いは、実装仕様に従う。

## 7. ファイル・画像の安全性

- ファイル名にパス区切り、相対パス、特殊文字が含まれる場合を確認する。
- 同名ファイル登録時に意図しない上書きが起きないことを確認する。
- 拡張子とMIMEタイプが一致しないファイルを拒否する。
- 画像拡張子でも画像実体でないデータを拒否する。
- ダウンロード時のファイル名が安全に扱われることを確認する。
- アップロードファイルを直接実行できないことを確認する。
- 権限外メモのファイルをファイルIDの直接指定で取得できないことを確認する。

## 8. 自動保存

次の状態を個別に確認する。

- 入力変更直後で未保存
- 入力変更から3秒経過し保存中
- 下書き保存成功
- 下書き保存失敗
- 下書き復元可能
- 本登録・本更新後に不要な下書きが残らない
- 本体更新後に下書きが古い

下書き保存に失敗しても、手動登録・更新は継続できることを確認する。

## 9. 同時編集制御

- 編集開始時点の`updatedAt`を保持する。
- 保存時点のDBの`updatedAt`と比較する。
- 値が異なる場合は更新を拒否し、HTTPステータス`409`を返す。
- 指定された競合メッセージを表示する。
- 競合時も入力中のタイトル、本文、タグを保持する。
- 最新内容を再取得して確認後、再編集・再保存できることを確認する。

## 10. パスワード

- パスワードをDBへ平文保存しない。
- APIレスポンス、ユーザー一覧、ログにパスワードを含めない。
- パスワード入力欄はマスク表示する。
- 最小・最大文字数の境界値を確認する。
- 大文字、小文字、数字、記号を含むパスワードを扱えることを確認する。

## 11. 下書きAPIのテスト対象

新規作成下書きと特定メモの編集下書きを区別する。共通APIを使用する場合でも、テストケースに対象種別と対象メモIDを明記する。

- `GET /api/drafts/new`
- `GET /api/drafts/memos/:memoId`
- `POST /api/drafts`
- 新規作成下書きの削除
- 編集下書きの削除

## 12. テスト結果の記録

- テストケースID
- 機能名
- テスト種別、重要度、対象
- 前提条件
- 使用ユーザー
- 使用データ
- 操作手順
- 期待結果
- 実際の結果
- HTTPステータスとレスポンス
- DB確認結果
- 合否
- 不具合番号
- 備考
